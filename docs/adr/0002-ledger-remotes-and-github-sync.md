# ADR 0002: Ledgers can come from, and sync to, an external git repository

**Status:** Accepted · 2026-10-20

## Context

Every ledger is already a git repository on the server, and every change Studio makes is a
commit. People keep ledgers on GitHub and want Studio to work on those repositories rather than
on a copy: create a ledger from an existing repository, and have each change land on GitHub
too. The one requirement voiced for authentication was "set it up once, for life": nothing
that expires and has to be re-entered.

## Decision

- **Sources.** A ledger can be created from any git URL the API server can reach over `https`
  or `ssh`, or from an absolute path on the server (administrators only, never inside the data
  directory). The clone keeps the full history; the main file is `main.bean`, else the only
  top-level ledger file, else the API asks which one. Plain `http` is refused. A ledger created
  from a template can be connected to a remote later and pushes its history on connection.
- **Credentials.** One SSH keypair per person, generated by the server and stored encrypted;
  the person adds the public half to their git host once, and it never expires. A token is the
  fallback for hosts without SSH access. Secrets are encrypted at rest under `BS_SECRET_KEY`
  (Fernet with an HKDF-derived key), are never written to `.git/config` or a command line
  (tokens go through a `GIT_ASKPASS` helper fed from the environment; SSH keys exist as a
  `0600` file only for the duration of a git call), and are never returned by the API. An SSH
  remote always uses the ledger owner's key, whoever connected it. OAuth apps, GitHub Apps and
  per-repository deploy keys were considered and set aside: the first two need a registration
  step and expire or rotate, the last needs setting up per repository.
- **Sync policy.** Every commit is pushed right after it lands, off the request path and
  serialized per ledger. Pulling is on demand: Sync fetches, fast-forwards or rebases local
  commits, and pushes. A conflict stops Sync with a `diverged` state and pauses pushes; an
  admin then keeps one side (reset to the remote, or overwrite the remote). Nothing is ever
  merged silently. The states are `in_sync`, `pushing`, `behind`, `diverged` and `error`.
- **Shape.** `ledger_remotes` (one row per ledger) and `user_ssh_keys` (one per person) hold
  metadata and ciphertext only; ledger content stays in git. `RemoteSync` in
  `apps/api/app/ledgers/remotes.py` owns the policy, the credentials and the state machine, and
  hooks the single `LedgerStore.commit` path through a listener. Git itself is the `git` CLI,
  as everywhere else in the API, with `GIT_ALLOW_PROTOCOL=https:ssh:file`, prompts disabled,
  GitHub's host keys pre-seeded and other hosts pinned on first use.

## Consequences

- The API image needs `openssh-client`; a server without `ssh` reports it on Test connection.
- Rotating `BS_SECRET_KEY` makes stored tokens and keys undecryptable; remotes then show an
  error until they are reconnected or the key regenerated.
- A single API process is assumed for the per-ledger locks, as the ledger store already does.
- Webhooks for inbound changes, non-default branches, several remotes per ledger and in-app
  conflict resolution are out of scope; `diverged` offers only the two blunt choices.
- Signed-in people can make the server contact any `https` or `ssh` host (Test connection,
  create, connect) and see git's error output, which reveals reachability. Studio is
  self-hosted for people who trust each other, so private address ranges are not blocked; the
  probe endpoint requires a browser session rather than an API key, and remote details are
  returned only to people who can write to the ledger.
- The clone size limit is enforced after the clone finishes, so an oversized repository
  occupies disk until the timeout or the size check removes it.
- Sync holds the ledger's write lock only while integrating remote commits; fetch and push run
  outside it, so edits are never blocked by a slow host for longer than a rebase takes.
